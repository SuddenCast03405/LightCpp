## 顺带修掉一个既有真 bug：数字高亮正则一直是无效的
- `CppSyntaxHighlighter` 的数字规则 `\b(...)?)|(...)|...)\b` 多了一个 `)`，
  Qt 报 `unmatched closing parenthesis` → 整条规则被 QSyntaxHighlighter 静默跳过，
  数字从来没被高亮过，而且每次重绘都往 stderr 刷 "called on an invalid QRegularExpression object"。
- 修复 = 把 alternation 收进外层 `\b(...)\b` 组（删掉一个括号）。用最小 Qt 程序验证：
  旧串 invalid / 新串 valid，且能匹配 42、0xFF、0b1010、1.5e3、10u、1'000，不误匹配标识符。

## 括号自动配对（CodeEditor）
用户诉求：输入时自动匹配另一个括号。

- `CodeEditor` 新增（`.hpp` 里加 `#include <QTextCursor>`）：
  - `autoCloseBracket(QChar typed)` → bool（是否已消化这次按键）
  - `backspaceEmptyPair()` → bool
  - 静态工具：`closingBracketFor()` / `isClosingBracket()` / `isQuote()` /
    `characterBefore(cursor)` / `characterAfter(cursor)`。
- 行为：`(` `[` `{` `"` `'` 插入成对、光标居中；**已有右半边则跳过它**（否则会得到 `())`）；
  有选区则**包裹**选区并保留选中状态；`"` 不配对时退回普通输入。
- `characterAfter()` 必须用 `position() >= characterCount() - 1` 判断结尾
  （QTextDocument 末尾有一个段落分隔符 `U+2029`，文档 `"()"` 的 characterCount 是 3）。
- **坑（backspaceEmptyPair 第一版有 bug）**：想删除 `(|)` 时用
  `movePosition(PreviousCharacter, KeepAnchor, 2)` —— 从 position 1 出发左移 2 个字符
  会**停在文档开头只选中 1 个字符**，结果只删掉 `(` 并把光标留在错误位置（`foo(|)` → `fo)`）。
  正确写法：`setPosition(pos - 1)` 再 `setPosition(pos + 1, KeepAnchor)`，最后 `removeSelectedText()`。
- 选区包裹**不能**用 `selectedText()` 重新插入：它会把段落分隔符变成字符 `U+2029`，
  多行选区会被写坏。改为在 `selectionStart`/`selectionEnd` 处分别 `insertText` 前后两半。
- 引号特例：前一字符是字母/数字/下划线且后面不是同种引号时**不配对**
  （C++ 的 `1'000` 数字分隔符、注释里的撇号、`foo"`）。
  **坑**：这条守卫必须带 `!cursor.hasSelection()` —— 选区存在时 `characterBefore()`
  取到的是选区前的字（如 `"foo"` 里的 `o`）而 `characterAfter()` 是段落符，
  守卫会把 `"` 对选区的包裹也拦掉，退化成"用 `""` 替换掉选区"。
- 在 `keyPressEvent` **最前面**拦截（早于补全逻辑），让自动插入的对表现得像普通输入
  （一次 undo 就能整体撤销）；`plainTextKey` 排除 Ctrl/Alt/Meta 修饰键。
- `"` 配对后仍要调 `requestCompletionAtCursor("\"")`：`"` 兼作 clangd 的 include 补全触发符，
  直接 `return` 会把原来的补全入口丢掉（回退到旧代码会插出第二个引号）。
- 验证：离屏 headless 测试 `%TEMP%\lightcpp_smoke\bracket_smoke.cpp`，
  用 `QKeyEvent` 真实驱动 `CodeEditor`，**31 项断言全过**（插成对 / 引号不配对 /
  跳过右半边 / 包裹选区 / Backspace 删空对 / 一次 undo / 只读文档不响应）；
  ctest 67/67 通过。

## 制表宽度 4 空格 / 过期二进制弹窗 / 新增 Program Output 通道
用户诉求：① 一个 Tab 改宽为 4 个空格（不是 10.5 个）；② Build Log 里
"Note: X.exe is older than the source — press F5 to rebuild." 改成独立对话框问是否重新编译；
③ 新增 Output 选项 "Program Output"，所有程序输出定向进去。

### ① 制表宽度
- `CodeEditor` 之前**从未调过 `setTabStopDistance`**，用的是 Qt 的 `QTextOption` 默认 80px；
  在 Cascadia Code 10pt（空格 8px）下正好 10 格 —— 这就是用户看到的"10.5 个空格宽"。
- 修复：构造函数 `setFont(font)` 之后加
  `setTabStopDistance(QFontMetricsF(font).horizontalAdvance(QLatin1Char(' ')) * 4.0)`，
  以空格宽度为基准算，换字体也自动跟着变（本机 = 32px）。顺手补 `#include <QFontMetrics>`。
- 有意思的巧合：`MainWindow::onCursorPositionChanged()` 里的状态栏列号换算写着
  `col += blockText.count('\t') * 3`（因为 col 已把 tab 算作 1 列），**本来就假设 tab = 4 列**。
  以前编辑器把 tab 渲染成 10 格、状态栏却报 4 格，两边一直对不上；现在一致了。

### ② 过期二进制 → 对话框
- 原逻辑（`onRunCurrentFile`）：exe 存在但比源码旧（或缓冲 modified）时只往 Build Log 打一句
  "Note: … press F5 to rebuild."，然后照跑旧的。
- 改为 `QMessageBox::question(this, tr("Source Changed"), …)`：Yes → `onCompileAndRun()` 并 return；
  No → 跑旧二进制，并在 Program Output 记一行 "Running the existing X without rebuilding."。
  两条分支的标题（"Not Compiled" / "Source Changed"）成了很自然的测试断言点。

### ③ Program Output 通道
- `OutputPanel::Channel` 加 `ChannelProgram`，**插在 Build Log 之后、Problems 之前**
  （Problems 从 2 变 3）。确认过没有 QSettings 之类按裸下标持久化的地方，全仓库都用枚举常量，
  所以重编号安全。同步加 `appendProgramOutput()` + `programOutput_` 页 + placeholder + `clearOutput()` 分支。
- `MainWindow` 侧把 run 相关的输出整体搬到新通道：`startProgram()` 里 runner 的 stdout、`--- Running:`、
  `--- Program exited with code N ---`、失败提示，以及 `onRunCurrentFile` / `onStopProgram` 的
  "No active file to run." / "Nothing to run yet" / "Hint:" / "--- Stopping program ---"。
  编译器侧（`onCompileCurrentFile` 与 compiler_ 的 finished 回调）留在 Build Log，包括
  "Build failed — nothing was run." ——它是构建结果，仍是 Build Log 的语义。
- 语义变成：**Build Log = 编译；Program Output = 运行控制台**（横幅 + 程序输出 + 退出码自成一份完整转录）。

## clangd 的 VFS 报错 + MSVC 单文件编译
用户诉求：① 修掉 `VFS: failed to set CWD to E:/msys64/tmp/lightcpp-untitled: No such file or directory`
（不影响功能但是个报错，修不好可以不管）；② 加 MSVC 单文件编译支持，覆盖 6.0 ~ 2026（18.x，说已有此版本）。

### ① VFS 报错：目录根本没建
- 未保存缓冲的虚拟路径是 `QDir::tempPath()/lightcpp-untitled/Untitled-N.cpp`，
  而**那个目录从来没被创建过**（编译用的 `lightcpp-compile/` 倒是建了，lint 用的这个漏了）。
  clangd 会把 VFS 的工作目录设成文档父目录，于是每次 didOpen 都报一次。
- 修复：`onNewFile()` 里 `QDir().mkpath(virtualDir)`。3 行，零风险。
- 顺带确认本机 `QDir::tempPath()` = `E:/msys64/tmp`（MSYS2 的 TMP），所以错误信息里的路径长那样。

### ② MSVC 支持
**为什么不用 vcvarsall.bat**：它是 cmd 脚本，内部要调 `reg.exe`。这台机器的沙箱把 `reg.exe` 列入程序黑名单，
一跑整条命令直接被拒（我第一次试就这么撞墙了）；而且 PowerShell 工具本身也禁止调用 `cmd.exe`。
索性把 vcvarsall 干的事自己在 C++ 里做掉——更快、可控，还顺带让 IDE 不依赖命令解释器。

**先做实验再写代码**（这几轮探测把设计定死了）：
- `vswhere.exe` 3.1.7 存在；**不加 `-prerelease` 看不到预览版**，加了才可能发现 VS 2026(18.x)。
  `-format json` 一次拿到 installationPath + installationVersion，比 `-property` 可靠
  （试过 `-property A -property B`，只回最后一个，配不上对）。
- 本机只有 **VS 2022 Professional 17.0 / toolset 14.30.30705 / cl 19.30.30715**，Windows SDK 10.0.19041.0。
  **18.x 和 VC6 都不存在**——用户说的"已有 18.x"与实际不符，如实告知。
- SDK **不在** `C:\Program Files (x86)\Windows Kits\10`，而在 `D:\Windows Kits\10`；
  权威来源是注册表 `HKLM\...\Windows Kits\Installed Roots` 的 `KitsRoot10`，别猜。
- 用**手工拼的 INCLUDE/LIB/PATH 直接跑 cl.exe 成功**（没经过任何 bat）：cl 19.30 → exit 0 → 产物能跑。
- 关键发现：`cl <绝对路径的源文件>` 而 CWD 在别处时，**exe/.obj 落在 CWD 而不是源文件旁边**。
  于是 `/Fe` 指定 exe、`/Fo` 把 obj 丢到 temp 就行。
- 又一个关键发现：**只加 `/Z7` 而不加 `/Zi` 之外的东西，linker 依然会在 CWD 掉 `.pdb`(6.5MB)+`.ilk`(3.2MB)**；
  换成完全不带调试信息（`/W4 /EHsc /MT` + `/Fe` + `/Fo`）后，源码目录里**只剩 .cpp 和 .exe**。
  于是最终决定 MSVC 这条路不生成调试信息——换来源码目录干净，而这条路径本来就是"编译一下跑起来"，不是调试。
- `/std:c++20` 在 19.30 上可用（exit 0）。

**实现**：新增 `MsvcToolchain.hpp/.cpp`（`LightCpp::App::Msvc`），`detect()` + `standardArgument()`。
- 检测顺序：vswhere（2017+）→ `SxS\VS7` 注册表（2002–2019）→ VS6 的键/经典 `VC98` 路径；按 VS 主版本打分取最新。
- 三种布局：`VC\Tools\MSVC\<ver>\bin\Hostx64\x64`（2017+）/ `VC\bin\amd64`+`VC\lib\amd64`（2002–2015）/ `VC98\{Bin,Include,Lib}`（VC6，仅 x86）。
- `standardArgument()` 按 cl 小版本降级（≥29 c++20 / ≥14 c++17 / ≥11 c++latest / 更老不传），
  小版本从工具集目录名 `14.30.30705` 取 30。传了编译器不认识的 `/std:` 是硬错误，必须降级而不是硬塞。
- 参数：`/nologo /W4 /EHsc /MT [/TP] [/std:...] /Fe<exe> /Fo<obj> <src>`。
  `/MT` = MinGW 侧 `-static-libgcc -static-libstdc++` 的对应物；`/TP` 修正"cl 按扩展名把 .h 当 C 编"。

## Ctrl+左键跳转定义（go to definition）
用户诉求：「现在添加跳转功能(Ctrl+左键的那个)」。

### LSP 侧
- `LanguageServerClient` 加 `textDocument/definition`，**完全照 `requestCompletion` 的模子**：
  `int requestDefinition(filePath, line, column)` 返回 JSON-RPC id（未 running / 文档未 didOpen 时返回 0），
  `QMap<int, QString> definitionRequests_` 记录 id→路径，`definitionReady(id, filePath, LspLocation)` 信号回传，
  `stop()` 里与 `completionRequests_` 一起清空。
- 新增 `struct LspLocation { QString filePath; int line, column; bool isValid(); }`，
  **空 filePath 就是"没找到"**——不用另开一个 found 标志，调用方判 `isValid()` 即可。
- 响应形状要兼容三种：`Location`（uri+range）/ `Location[]` / `LocationLink[]`
  （`targetUri` + `targetSelectionRange`）。`LocationLink` 优先取 **targetSelectionRange**，
  否则光标会落在返回类型或前导属性上而不是标识符。非 file:// URI（clangd 对 builtin 会这么答）
  `fromFileUri()` 得到空串 → 自然变成"没找到"，正好。

### 编辑器侧
- `CodeEditor::mousePressEvent`：`左键 + CtrlModifier` → `cursorForPosition()` 取位置，
  **先算位置再交给基类**（基类会移动光标，有选区时会改变指针下的字符），**发信号放在基类之后**，
  这样答案回来时本地光标已经安定。
- 用 `event->position().toPoint()` 而不是 `event->pos()`——**Qt6 里 `QMouseEvent::pos()` 已弃用**，
  本仓库 `-Werror` 会直接编译失败。
- F12 是键盘孪生：`keyPressEvent` 最前面拦 `Qt::Key_F12`，用**光标**位置发同一个信号。

### MainWindow 侧

  （lint 的 didChange 有 300ms 防抖，否则 clangd 拿旧文本算位置），再 `requestDefinition`，
  id 进 `pendingDefinitions_`（`QPointer<CodeEditor>`）。
- `definitionReady` 里 `latestDefinitionId_` 守卫（慢响应不许把视图拽走），

  未保存缓冲是虚拟路径不能从磁盘重开；匹配不到才 `openFileInTab`）——Problems 列表与跳转定义
  从此共用一条路径，`onProblemActivated` 退化成一行转发。

## 踩坑：并行编辑同一个文件会互相覆盖
本轮三次丢了改动（`requestDefinition` 声明、`jumpToLocation` 声明与实现、`CodeEditor::mousePressEvent` 整个函数体），
症状是**编译报"未声明"而源码里看起来明明写了**。原因：对**同一个文件**发的多个 Edit 是并行执行的读-改-写，

## clangd 跟随所选编译器的头文件 + 去掉 MSVC 的 /std:c++20
用户诉求（附截图：MSVC 已选中，但打开的 `<iostream>` 是 GCC/libstdc++ 的头）：
「在使用MSVC工具链时clangd应当读取对应编译器的头文件等而不是自身的, 去掉msvc的/std:c++20」。

### 先做实验，把机制定死（这一步很值）
- **`--query-driver` 对 MSVC 无效**：没有编译数据库时 clangd 用 fallback 命令，driver 恒为 `clang`，
  日志直接写 `System include extraction: driver clang expanded to .../clang.exe` + `not allowed driver`。
  白名单里放 cl.exe 也救不了——那个 driver 名字就不叫 cl。
- 实测 clangd 默认：`-triple x86_64-w64-windows-gnu`，`-internal-isystem E:/msys64/ucrt64/.../include/c++`
  ——截图里那份 GNU 头的来源就在这。
- **唯一可行机制 = 编译数据库**。实测 `compile_flags.txt`（一行一个参数）+ `--compile-commands-dir` 之后，
  cc1 args 变成 `-triple x86_64-pc-windows-msvc19.30.0` + 4 个 `-isystem`（MSVC 工具集 + SDK ucrt/shared/um），
  `<iostream>`/`<vector>` **All checks completed, 0 errors**。
- 顺带验证 `-fms-compatibility-version=19.30` 能覆盖 clang 自己的默认 19.33（triple 变成 `msvc19.30.0`）。

### 实现
- 新增 `ToolchainHeaders.hpp`（`target` / `extraFlags` / `includeDirs` + `isEmpty()` + `operator==`）。
  单独成一个头，是为了不让 `MsvcToolchain` 去依赖 LSP 客户端。
- `LanguageServerClient`：`setToolchainHeaders()` / `toolchainHeaders()`；`start()` 里 `writeClangdFlags()`
  写到 **`<temp>/lightcpp-clangd/compile_flags.txt`**，再挂 `--compile-commands-dir`。
  空配置不加这个开关——GCC/Clang 就靠这条保持 clangd 自带的默认。
- `Msvc::clangdHeaders()`：target 用新的 `targetTriple`；`extraFlags` 是 `-fms-compatibility` /
  `-fms-extensions` / `-fms-compatibility-version=19.<clMinor>`；`includeDirs` 直接复用
  `Toolchain::includeDirs`（与 cl.exe 的 INCLUDE 同一批目录，构造上不可能不一致）。
- **`-std:` 一个都不传**：clang 对 msvc target 的默认就是 c++14，正好等于 cl.exe 不带 `/std:` 的默认，
  日志里能看到 `Indexing c++14 standard library`——两边语言级别天然一致，比硬写一个标准更贴合
  "跟随对应编译器"的意图。

  并在 Clangd Log 记一行 "Restarting the language server for …"。构造里在
  `actSyntaxCheck_->setChecked(true)` **之前**调一次，clangd 一上来就是对的。

### 测试顺带挖出一个真 bug：重启后 clangd 永远初始化不了
`handleMessage()` 判断 initialize 响应用的是**写死的 `id == 1`**。而 `nextRequestId_` 跨重启不清零，
第二次 start 的 initialize 拿到的是 3 → 永远匹配不上 → `initialized_` 一直 false → 不发 didOpen →
诊断再也不出现。也就是说 **Tools 菜单里"语法检查"关掉再打开本来就是坏的**（没人发现是因为没人重启过 LSP）。
修复：加成员 `initializeRequestId_`，start 时记住、handleMessage 时比对。日志证据很直白：
重启后只有 `--> reply:initialize(3)`，没有 `<-- initialized`、没有 didOpen。
