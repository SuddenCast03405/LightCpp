## 修复 GBK/GB18030 被误判为 EUC-KR (2026-09-19 晚)

### 问题根因
GBK 与 EUC-KR 双字节字符字节范围高度重叠（GBK 0x81-0xFE+0x40-0xFE，
EUC-KR 0x81-0xFE+0x41-0xFE），几乎所有合法 GBK 文件也是合法 EUC-KR 文件。
原评分权重不对称：`other hanzi +5` < `hangul +6`，当 GBK 文件的中文字符
不在 ~120 字常用表时，EUC-KR 误解码反而得 +6/char 胜出。

### 修复方案
1. **评分调整**：`other hanzi +5 → +7`（高于 Hangul +6）
2. **常用汉字表扩展**：~120 字 → ~350 字（覆盖更多中文常用字）
3. **新增 `candidatePlausible()` 硬过滤**：基于解码后的字符构成做硬性判别
   - EUC-KR 候选：要求 hanzi == 0（韩文解码不应产生汉字）
   - GBK/GB18030/Big5 候选：要求 `anchors >= 2 && anchors*3 >= hanzi`
     （anchors = common hanzi + 中文标点，必须占汉字数 ≥ 1/3）
   - ShiftJis 候选：hangul == 0
4. **加入 Gbk 到 kLegacyCandidates**（先于 GB18030）：让纯 GBK 文件直接
   参与打分，报告更具体的 GBK 名称
5. **minimumScore 从 3 降到 1**：硬过滤已足够严格，分数门槛只过滤近乎
   无意义的解码

### 测试结果
- 新增 5 个回归测试：罕见汉字 GBK、混合 ASCII GBK、纯中文标点 GBK、
  反向韩文不被误判为 GBK（2 个场景）
- 全量 66/66 测试通过
- 真实 GBK 文件端到端 CLI 验证：3 个测试文件全部正确识别为 GBK

## 改用本地 ANSI fallback 算法 + 编码下拉框 (2026-09-19 夜)

### 用户反馈
GBK/GB18030 仍被识别为 EUC-KR。原算法（评分 + 硬过滤）在真实场景仍不可靠。

### 新算法（彻底简化）
- BOM 检测 → 对应 Unicode 编码
- NUL 结构检测 → UTF-16/32 或 binary
- UTF-8 严格校验 → UTF-8
- **不是 Unicode → 直接返回本地 ANSI 编码**（不再走 legacy 评分）
  - zh-CN Windows：返回 GBK（CP936）；ja-JP：Shift-JIS；ko-KR：EUC-KR；en-US：Windows-1252
  - 通过 Windows API `GetACP()` 获取系统 ANSI 代码页

### 新增接口
- `LightCpp::Text::localAnsiEncoding()` — 返回本地 ANSI 对应的 TextEncoding
- `LightCpp::Text::localAnsiDisplayName()` — 返回 "ANSI (GBK)" 等显示名
- `readTextFileWithEncoding(path, encoding, options)` — 用指定编码强制读取文件
  （用户从下拉框选择时调用，跳过自动检测）

### GUI 编码下拉框（已启用，用户可切换）
- 第一项：UTF-8
- 第二项：ANSI (<本地编码>) — 用 `localAnsiDisplayName()` 填充
- 其他：按名称字母排序（Big5, EUC-KR, GB18030, ISO-8859-1, Shift-JIS,
  UTF-16BE/LE, UTF-32BE/LE, Windows-1252）
- 用户切换时调用 `reloadWithEncoding(encoding)` 重新加载当前文件
- QComboBox itemData 存 `TextEncoding` enum（需 `Q_DECLARE_METATYPE`）

### 测试调整

- 新增 `LocalAnsi.*` 测试（验证 `localAnsiEncoding()` 和 `localAnsiDisplayName()`）
- 新增 `NonLocal*FallsBackToLocalAnsi` 测试（验证 Big5/ShiftJis/EUC-KR/Latin1
  在 zh-CN 下都被识别为 GBK）
- 新增 `ReadsShiftJisWithForcedEncoding` / `ReadsBig5WithForcedEncoding`
