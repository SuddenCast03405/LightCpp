## 一、结论摘要

| 严重度 | 数量 | 说明 |
| --- | --- | --- |
| 高 | 3 | 崩溃、层级越权漏检、类型错误漏检 |

**一句话**：这套工具在"数据是好的"时候完全正确；它现在的短板是**防坏数据的能力**——而这恰好是校验器存在的唯一理由。

## 二、高风险问题

### H1 · `dependencies` 写错类型会导致 validate 直接崩溃

- **位置**：`tools/lightcpp_pm.py:342`、`:364`（`(p.get("dependencies") or {}).items()` / `for dep in ...`）
- **复现**：把 `plugins/gdb/plugin.json` 的 `"dependencies"` 从对象改成数组 `["cpp-base"]`，执行 `validate`
- **实际输出**：`AttributeError: 'list' object has no attribute 'items'`（异常逃逸，栈回溯直接糊在终端上）
- **影响**：CI 从"报告哪个插件写错了"退化为"Python 崩了"，新人只能自己读栈。
- **修复**：加载阶段做一次类型规整，非法类型记为 `E001` 并跳过该插件的后续语义检查。

### H2 · `capabilitySets` 写错类型 → `info` 崩溃、`validate` 报 14 条无意义错误

- **位置**：`tools/lightcpp_pm.py:437-441`
- **复现**：`"capabilitySets": "debug.breakpoint"`（少写方括号）
- **实际输出**：`info gdb` → `KeyError: 'd'`（按字符遍历字符串，把 `d` 当功能集 ID）；`validate` 报 14 条 E010/E022
- **影响**：错误提示指向"插件不存在"，而真正的错因是一对方括号，误导性极强。

### H3 · 层级越权完全无人把关

- **位置**：`check_invariants` 的 `layerDependency` 规则（`tools/lightcpp_pm.py:308`）只检查"某层依赖了什么"，不检查"谁有资格进这一层"
- **复现**：把 `gdb` 的 `layer` 改成 `core`（仍依赖 `cpp-base`）
- **实际输出**：**0 个错误**；`resolve gdb` 得到 `['cpp-base', 'gdb']`，`graph` 里 `gdb` 出现在「核心基础层」
- **影响**：`docs/ARCHITECTURE.md` 写着"核心层只有 `cpp-base`"，而工具无法保证这条。任何插件改个字段就能冒充核心层。
- **修复**：新增不变量类型 `layerMembers`（`core` 只能是 `cpp-base`；`build-framework` 只能是 `build-core`；`pack` 层只能是 `kind=pack`）。

## 三、中风险问题

### M1 · 校验覆盖不到 Schema 声明的约束

Schema（`schemas/plugin.schema.json`）写了 `additionalProperties: false`、`description.minLength: 8`、`id.pattern`，但 `validate` 一个都没查：

| 篡改 | Schema 应拒绝 | validate 实际 |
| --- | --- | --- |
| 加一个拼错的键 `"dependecies"` | ✅ | ❌ 无错误 |
| `description: "x"` | ✅ | ❌ 无错误 |
| `contributes.commands` 写成字符串 | ✅ | ❌ 无错误 |
| `platforms: "linux"`（应为数组） | ✅ | ❌ 只有 5 条 E009，后续 matrix 输出 `l,i,n,u,x` |

**风险**：拼错 `dependencies` 是最典型的静默事故——插件看起来装了依赖，实际没有任何约束。

### M2 · 功能目录缺少结构校验

| 篡改 | 结果 |
| --- | --- |
| 复制粘贴导致两个功能集 `id` 相同 | ❌ 无错误（后者覆盖前者，功能静默丢失） |
| 功能集 `domain` 写成不存在的值 | ❌ 无错误（`coverage` 统计里凭空消失） |
| 功能 `except` 指向不存在的插件名 | ❌ 无错误（排除规则永远不生效） |

### M3 · 表格渲染不转义管道符

- **位置**：`render_table`（`:60`）
- **复现**：`nameZh` 改成 `GDB|测试` 后 `docs` 生成
- **结果**：Markdown 表格被拆列，该行错位
- **影响**：桌面/IDE 类插件描述里出现 `a|b` 非常常见（如 "Debug|Release"），迟早踩到。

### M4 · 契约规则覆盖不全

`catalog/invariants.json` 只锁定 8 条。以下规划要求**目前只靠人工**：

- 每个 `build-system` 插件必须声明 `contributes.buildSystems`（否则装了也构建不了）
- 核心层不得声明 `capabilitySets` 之外的业务贡献点
- `ninja` 必须被 CMake/Meson 的 `recommends` 引用（当前有 E101，但反过来"ninja 被谁引用"无人校验）
- `cmd_*` 系列没有断言函数调用形态，`cmd_graph` 依赖 `args.layer`/`args.format`，被单独调用即 `AttributeError`（测试里靠 `type('a',(),{...})()` 造壳绕开，说明接口耦合了 argparse）

### M5 · CI 与 README 的"绿色"缺乏可操作的失败信息

- `docs --check` 成功时**零输出**，失败时才打印——本地跑分不清"通过"和"没跑"
- `validate --strict` 与 `validate` 的差别只体现在"消失的 W002"，没有汇总行说明有多少条被抑制

### 7.2 修复过程中发现的更严重缺陷（自查自纠）

修改 `_load` 时先写成了：

```python
n.bad.extend(f"{rel}: {m}" for m in n.bad)   # ❌ 自引用
```

`list.extend` 会边迭代边追加，列表无限增长直到进程被 OOM Killer 杀掉（退出码 137、无任何输出）。这比原来的 `AttributeError` 更危险——**静默地把 CI 杀死，看起来像"卡住了"**。

已改为先构建独立列表 `issues = [...]` 再赋值，并改用 `self.type_errors` 而非插件对象自身。这一条也写进了测试：同一用例同时断言"不崩溃"和"能报出 E001"。
